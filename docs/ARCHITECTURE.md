# Architecture

The Qt UI and laptop skills are future consumers of the same async core.
Phase 1 executes this sequence:

1. Load and validate one config/.env pair; construct only the chosen brain.
2. Before voice mode, load local STT while the microphone is closed.
3. Wait for an explicit PTT gesture. A keyboard listener does not create a mic stream.
4. Open a bounded microphone stream. Stop on Enter, release, `/mute`, quit or the time cap.
5. Close the stream, reject empty/silent capture, transcribe locally from an in-memory WAV.
6. Stream the transcript and recent RAM context through the selected brain adapter.
7. Segment generated text into phrases and feed a bounded playback queue.
8. Stream Edge MP3 chunks into a fixed player, or use an explicitly configured local engine.
9. Commit only successful full conversation turns to bounded RAM context; return idle/muted.

`Assistant` owns history, serialized replies and state events. `TerminalRunner` owns input,
capture and command handling. Neither knows about Qt. `Brain` and `Speaker` protocols allow
injected implementations for tests. SDKs have bounded timeouts; HTTP/provider error bodies
do not cross the public error boundary. Microphone and playback resources close on cancellation.

The synchronous audio/STT libraries run in worker threads. Audio stop is cooperative and
the stream closes before the canceled task completes. Terminal input uses the macOS/POSIX
event-loop reader so a time-capped capture does not leave a blocked `input()` thread.
Windows console fallback needs its own physical cancellation testing.

No audio, transcript or chat response is written by the runtime. The local log accepts only
an allowlist of metadata keys. The future SQLite memory store is not present yet.

## Phase 2 plugin boundary (planned)

Each skill module will export a unique `name`, `description`, JSON `schema`, and async
`run(arguments)` function. A separate policy layer, not the model or skill description,
will enforce risk classification, allowlisting and confirmation.

The brain can propose tools but cannot bypass schema validation or directly execute code.
An exact pending action/arguments record will be bound to a specific confirmation request,
expire promptly and be consumed once. A generic old “yes” must never authorize a new action.
The model receives the structured outcome after execution before producing a user-facing claim.

Keep module import side effects minimal. Dynamic registration must not mean executing
untrusted downloaded plugins, names generated by the LLM or arbitrary filesystem modules.

## Phase 3 UI boundary (planned)

Qt remains on the main thread; an async worker coordinates voice and brain tasks.
Signals carry state and playback amplitude/viseme hints into the sprite animator.
Mute must stop live recording/wake capture and playback, cancel pending action confirmations,
and visibly show the muted state. Screenshots, desktop observations and OS control cannot
be initiated merely by pet animation or background conversation.
